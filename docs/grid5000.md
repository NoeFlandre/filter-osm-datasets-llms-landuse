# Operations runbook (Grid'5000)

The controller runs on your machine. The frontends receive only light commands: `oarstat`,
`oarsub`, `oardel`, `usagepolicycheck -t`, one status-API call for each cycle, and small
rsyncs. Heavy work always runs on reserved nodes.

The operational defaults (sites, bucket, walltimes, caps, CUDA module, output namespace) are in
`luf.toml` at the repo root (or the file that `$LUF_CONFIG` names). CLI options override them.

```bash
export UV_PROJECT_ENVIRONMENT=~/.venvs/luf LUF_WORK=~/luf-work
luf g5k inventory        # refresh eligible GPU clusters (CC >= 8.0, >= 16 GB, x86_64, abaca/default)
```

## 1. Admit a GPU type (once for each type)

```bash
luf bench plan           # the 25,500-item benchmark as work (once)
luf g5k run --datasets benchmark --namespace gpu-<key> --gpu-models <key> \
    --sites grenoble,lille,lyon,nancy,rennes,sophia --besteffort --max-jobs 5
luf bench admit --gpu <key>   # exit 0 = admitted, 3 = rejected; writes gates/admission/<key>.json
```

GPU keys come from `luf g5k inventory`, for example `a100_sxm4_40gb`, `a40` or `l40s`.
To admit several types at the same time, use one process with a shared view of each
site for each cycle. The process queries each site one time for each cycle, for any number of GPU types:

```bash
luf g5k run-admission --gpus a100_pcie_40gb,h100_nvl,l40s
```

## 2. Plan a dataset (CPU job, resumable)

```bash
luf g5k cpu-job plan --site grenoble --dataset <dataset> --revision <sha>
```

Each job scans the input files on node-local scratch and emits chunks. It saves a checkpoint of its
SQLite index to the bucket every 15 minutes and on SIGTERM. Submit the job again until
`plans/<dataset>/<fp>/report.json` in the bucket shows `files_done == files_total`.

## 3. Generate (production)

```bash
luf g5k run --datasets <dataset> \
    --sites lille,lyon,nancy,rennes,sophia,grenoble --max-jobs 12 --max-jobs-per-site 4
```

Without `--gpu-models`, the controller uses only admitted GPU types. The nodes read the inputs from the
bucket. They upload each part and its manifest during the run. The controller pulls only
the manifests. To see the progress, run `luf status --datasets <dataset>`.

Each finished job writes `jobs/<site>/<job>.json` with a timeline (`started_at`,
`env_ready_seconds`, `engine_ready_at`, `first_result_at`, `last_result_at`, `ended_at`,
`walltime_s`, `assigned_texts`; ISO UTC, from the monotonic clock). `luf status` reports
`useful_fraction` for all jobs and for each GPU type. It is the generation seconds (`last_result_at -
engine_ready_at`) divided by the walltime. `luf status` also reports two shares of jobs:

- The share of jobs that stopped early (all assigned work done, no signal, more than 10 % of the walltime left).
- The share of jobs that ran to the checkpoint signal.

This summary ignores the records that the project wrote before the timeline existed.

## 4. Publish (CPU job, incremental)

```bash
luf g5k cpu-job publish --site grenoble --dataset <dataset> --revision <sha>
```

The first run mirrors the input repo. Each run adds `labels/` for the files that are fully generated,
the matching `generations/` and an updated card. A new run uploads only
the new data.

## Pause, resume, stop

```bash
luf g5k pause            # stop submitting; running jobs finish their walltime
luf g5k pause --cancel   # also oardel every luf-* job
luf g5k resume
```

It is always safe to kill the controller process. Its state is in `$LUF_WORK`.

## Usage policy as enforced

| Rule | Where |
|---|---|
| Weekday 09:00–19:00: only jobs of ≤ 1 h that start now (quota-exempt) | `domain/policy.py` |
| Nights and weekends: `-t night`, ending before the next working-day 09:00 | `domain/policy.py` |
| Abaca clusters: `-q abaca`; default clusters: `-q default` (always explicit) | `domain/capacity.py` |
| Besteffort: `--checkpoint 60`, and only where the account has no regular access | `domain/capacity.py`, controller |
| `usagepolicycheck -t` before and after each submission | controller |
| The controller cancels waiting jobs that OAR predicts to start more than 15 min late, and backs off the cluster | controller |
| The controller inspects or cancels only `luf-*` jobs | `adapters/g5k.py` |

## Logs and debugging

On the site, `~/luf/logs/<jobid>.out` has the `luf:` progress lines and
`<jobid>.err` has the SGLang and OAR output. The assignments are in
`$LUF_WORK/assignments/`. The job summaries are in the bucket under `jobs/`.

## Publish run times

You can resume `luf node publish` at each step: the mirror (parallel downloads, one commit for each 200
files, recorded in the mirror ledger), each partial commit and the card refresh that follows it.
The jobs do not read the result parts again. The resolution index goes through the bucket as
`index/resolve-<fp>.sqlite`. A job reads only the parts that it has not seen (ADR-0026) and saves the index
every 5 minutes. The job commits ready partial files at least every 10 minutes.
Thus a walltime stop loses a maximum of one batch. Submit the job again until it reports
that all sentences are labelled. The first run takes approximately one hour for a dataset of 400 files.
It takes several hours for the wiki mirror of more than 700 files. If the labelled share of a partial file
cannot change, the job only reads the file (one index lookup for each sentence). It does not rebuild the file.

### Keep publishing until done

```bash
luf g5k publish-loop --dataset <dataset> --revision <sha> --site grenoble \
    [--walltime-minutes 60] [--interval-seconds 300] [--max-interval-seconds 1800]
```

Each `--interval-seconds`, the loop reads `published/<dataset>.status.json` from the bucket.
If the file says `done: true` for this revision, the loop exits. Otherwise, the loop checks `oarstat`.
If no job named `luf-publish-<dataset[:20]>` waits or runs on the site, the loop submits
`cpu-job publish` (same deployment, walltime and policy checks). Publish jobs have their own OAR
name. Thus a planning loop (`luf-plan-<dataset>`) does not take them for planning. If a step fails
(slow `usagepolicycheck`, ssh timeout, bucket error), the loop logs the failure. It retries after a pause
that doubles for each consecutive failure, up to `--max-interval-seconds`. A failure never stops the loop.

Each publish run writes the marker, also a stopped run. The marker looks like this:

```json
{"dataset": "wiki", "revision": "<sha>", "files": {"total": 700, "complete": 512,
 "partial": 30, "unscanned": 0}, "mirrored": true, "stopped": "deadline", "done": false}
```

`done` is true only when all these conditions are true:

- The input mirror is complete.
- The planner index has no unscanned file.
- Each scanned file is fully labelled.
- Nothing stopped the run early.

### Graceful stop at the walltime

`luf node publish` handles SIGTERM, SIGUSR2 (the OAR `--checkpoint 300` warning, 5 minutes before
the end) and SIGINT. `scripts/node_job.sh` exports `LUF_JOB_DEADLINE_EPOCH` (job start plus
the walltime from `oarstat -j $OAR_JOB_ID -J`, or `OAR_JOB_WALLTIME_SECONDS`). It skips this without a message when
neither value is available. The job stops the start of new files on the signal, or 6 minutes before the
deadline, whichever is first. Then the job does these steps:

1. Finish the file in progress.
2. Upload the partial sink and the generations of the files that it completed.
3. Refresh the card from the ledgers.
4. Save each ledger and the card marker to the bucket.
5. Print `luf: publish stopped early (<reason>)` and exit with code 0.

The JSON report has `"stopped": "signal SIGUSR2"` or `"deadline"` (`null` for a run that
finished). A stop in the mirror occurs between batches. Thus the mirror ledger matches the
commits and the next job resumes. The job also saves the ledgers if the run crashes.

## Refreshing only the card

A full publish uses its first hour to restore the planner index and the result parts. A 1-hour
day walltime can be too short for this. To update only the Hub card (and map) from the ledgers in the bucket, run:

```bash
luf g5k cpu-job card --site grenoble --dataset <dataset> --revision <sha> --walltime-minutes 60
```

(on the node: `luf node publish --card-only`). 6 parallel workers read the missing counts for each file from the Hub.
The job saves the stats ledger to the bucket after each batch of 25 files. The job skips a file that
fails and counts it in the next run. A dataset with only a mirror keeps its card. See
ADR-0021.

## Storage hygiene

- **Sites:** only `~/luf/` belongs to the project. It has the code (`code/<commit>`; delete it
  when no job uses that commit), the logs, the spool (`work/`), the caches
  (`cache/hf`, `cache/flashinfer`, finished `cache/venv-*`) and `hf_token`.
  To check, run `luf g5k storage`.
- **Controller machine:** `$LUF_WORK` stays small (ledger, manifests). Delete it and
  the venv when a campaign is finished and published.

## Token

The owner puts a fine-grained token at `~/luf/hf_token` (mode 600) on each site.
Jobs export it to their own environment. Nobody else can read, print or copy it.
