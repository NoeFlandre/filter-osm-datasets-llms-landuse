# Operations runbook (Grid'5000)

The controller runs on your machine. Frontends only receive light commands: `oarstat`,
`oarsub`, `oardel`, `usagepolicycheck -t`, one status-API call per cycle, and small
rsyncs. Heavy work always runs on reserved nodes.

Operational defaults (sites, bucket, walltimes, caps, CUDA module, output namespace) live
in `luf.toml` at the repo root (or the file named by `$LUF_CONFIG`); CLI options override them.

```bash
export UV_PROJECT_ENVIRONMENT=~/.venvs/luf LUF_WORK=~/luf-work
luf g5k inventory        # refresh eligible GPU clusters (CC >= 8.0, >= 16 GB, x86_64, abaca/default)
```

## 1. Admit a GPU type (once per type)

```bash
luf bench plan           # the 25,500-item benchmark as work (once)
luf g5k run --datasets benchmark --namespace gpu-<key> --gpu-models <key> \
    --sites grenoble,lille,lyon,nancy,rennes,sophia --besteffort --max-jobs 5
luf bench admit --gpu <key>   # exit 0 = admitted, 3 = rejected; writes gates/admission/<key>.json
```

GPU keys come from `luf g5k inventory`, for example `a100_sxm4_40gb`, `a40` or `l40s`.
To admit several types at once, use one process with a shared per-cycle view of each
site (each site is queried once per cycle, whatever the number of GPU types):

```bash
luf g5k run-admission --gpus a100_pcie_40gb,h100_nvl,l40s
```

## 2. Plan a dataset (CPU job, resumable)

```bash
luf g5k cpu-job plan --site grenoble --dataset <dataset> --revision <sha>
```

Each job scans input files on node-local scratch, emits chunks, and checkpoints its
SQLite index to the bucket every 15 minutes and on SIGTERM. Resubmit it until
`plans/<dataset>/<fp>/report.json` in the bucket shows `files_done == files_total`.

## 3. Generate (production)

```bash
luf g5k run --datasets <dataset> \
    --sites lille,lyon,nancy,rennes,sophia,grenoble --max-jobs 12 --max-jobs-per-site 4
```

Without `--gpu-models`, only admitted GPU types are used. Nodes read inputs from the
bucket and upload each part plus its manifest as they go; the controller pulls only
manifests. Watch progress with `luf status --datasets <dataset>`.

Each finished job writes `jobs/<site>/<job>.json` with a timeline (`started_at`,
`env_ready_seconds`, `engine_ready_at`, `first_result_at`, `last_result_at`, `ended_at`,
`walltime_s`, `assigned_texts`; ISO UTC, derived from the monotonic clock). `luf status` reports
`useful_fraction` overall and per GPU type: generation seconds (`last_result_at -
engine_ready_at`) over walltime, the share of jobs that stopped early (all assigned work done,
not signalled, more than 10 % of the walltime left) and the share that ran to the checkpoint
signal. Records written before the timeline existed are ignored by this summary.

## 4. Publish (CPU job, incremental)

```bash
luf g5k cpu-job publish --site grenoble --dataset <dataset> --revision <sha>
```

The first run mirrors the input repo; each run adds `labels/` for fully generated
files, the matching `generations/` and an updated card. Re-running uploads only
what is new.

## Pause, resume, stop

```bash
luf g5k pause            # stop submitting; running jobs finish their walltime
luf g5k pause --cancel   # also oardel every luf-* job
luf g5k resume
```

Killing the controller process is always safe: its state lives in `$LUF_WORK`.

## Usage policy as enforced

| Rule | Where |
|---|---|
| Weekday 09:00–19:00: only jobs of ≤ 1 h that start now (quota-exempt) | `domain/policy.py` |
| Nights and weekends: `-t night`, ending before the next working-day 09:00 | `domain/policy.py` |
| Abaca clusters: `-q abaca`; default clusters: `-q default` (always explicit) | `domain/capacity.py` |
| Besteffort: `--checkpoint 60`, and only where the account has no regular access | `domain/capacity.py`, controller |
| `usagepolicycheck -t` before and after every submission | controller |
| Waiting jobs predicted to start more than 15 min late are cancelled, and the cluster backed off | controller |
| Only `luf-*` jobs are ever inspected or cancelled | `adapters/g5k.py` |

## Logs and debugging

On the site, `~/luf/logs/<jobid>.out` holds the `luf:` progress lines and
`<jobid>.err` holds SGLang and OAR output. Assignments are in
`$LUF_WORK/assignments/`, and job summaries in the bucket under `jobs/`.

## Publish run times

`luf node publish` is resumable at every step: the mirror (parallel downloads, one commit per 200
files, recorded in the mirror ledger), every partial commit and the card refresh that follows it.
A walltime stop therefore loses at most one batch; just submit the job again until it reports
everything labelled. Expect roughly an hour for the first run of a 400-file dataset and several for
the 700+ file wiki mirror; a partial file whose labelled share cannot have changed is only read
(one index lookup per sentence), never rebuilt.

### Graceful stop at the walltime

`luf node publish` handles SIGTERM, SIGUSR2 (OAR's `--checkpoint 300` warning, 5 minutes before
the end) and SIGINT, and `scripts/node_job.sh` exports `LUF_JOB_DEADLINE_EPOCH` (job start plus
walltime from `oarstat -j $OAR_JOB_ID -J`, or `OAR_JOB_WALLTIME_SECONDS`; skipped silently when
neither is available). The job stops starting new files on the signal, or 6 minutes before the
deadline, whichever comes first. It finishes the file in hand, uploads the partial sink and the
generations of the files it completed, refreshes the card from the ledgers, saves every ledger and
the card marker to the bucket, prints `luf: publish stopped early (<reason>)` and exits 0. The
JSON report carries `"stopped": "signal SIGUSR2"` or `"deadline"` (`null` for a run that
finished). A stop inside the mirror happens between batches, so the mirror ledger matches the
commits and the next job resumes. The ledgers are also saved if the run crashes.

## Storage hygiene

- **Sites:** only `~/luf/` is ours. It holds code (`code/<commit>`, safe to delete
  once no job uses that commit), logs, the spool (`work/`), caches
  (`cache/hf`, `cache/flashinfer`, finished `cache/venv-*`) and `hf_token`.
  Check with `luf g5k storage`.
- **Controller machine:** `$LUF_WORK` stays small (ledger, manifests). Delete it and
  the venv once a campaign is finished and published.

## Token

The owner places a fine-grained token at `~/luf/hf_token` (mode 600) on each site.
Jobs export it to their own environment. Nobody else reads, prints or copies it.
